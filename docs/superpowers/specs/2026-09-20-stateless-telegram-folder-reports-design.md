# Упрощённый бот отчётов по Telegram-папкам

**Дата:** 2026-09-20  
**Статус:** согласованный дизайн, ожидает финального просмотра владельцем

## 1. Цель

Заменить текущую архитектуру с PostgreSQL, постоянным сбором сообщений и
отдельным AI-worker одним лёгким сервисом. Сервис должен по расписанию и по
нажатию кнопок загружать сообщения за последние 24 часа непосредственно из
двух папок Telegram, выполнять два специализированных анализа через Codex и
отправлять результаты владельцу в личный диалог с ботом
`@moex_digest_1337_bot`.

Главное ограничение — минимальная постоянная нагрузка на небольшой сервер, где
уже работают другие важные боты.

## 2. Пользовательский сценарий

В личном чате владельца с ботом отображается постоянная клавиатура:

- `Дайджест сейчас`;
- `Настроение сейчас`;
- `Статус`.

Доступ к кнопкам и командам разрешён только пользователю из
`OWNER_TELEGRAM_ID`.

Автоматическое расписание в часовом поясе `Europe/Samara`:

- в 15:00 формируется дайджест по папке `Посты`;
- в 16:00 формируется отчёт о настроении по папке `Чаты`.

Ручной и автоматический запуск используют один и тот же код и всегда строят
окно `[время запуска − 24 часа, время запуска]`.

## 3. Источники данных

Источники определяются нативными папками диалогов Telegram, доступными через
MTProto:

- папка `Посты` содержит каналы для дайджеста;
- папка `Чаты` содержит группы и супергруппы для анализа настроения.

Имена папок сопоставляются без учёта регистра и с удалением пробелов по краям.
Из папки `Посты` принимаются только каналы. Из папки `Чаты` принимаются только
группы и супергруппы. Источники неподходящего типа пропускаются и отражаются в
статусе предупреждением.

Для анализа используются текст сообщений и подписи к медиа. Пустые сообщения,
служебные события и неподдерживаемый контент пропускаются. Сообщения за
пределами 24-часового окна не передаются в Codex.

## 4. Архитектура

В Docker Compose остаётся один постоянно работающий сервис `app`. Он включает:

1. aiogram-бота с owner-only проверкой доступа;
2. APScheduler с часовым поясом `Europe/Samara`;
3. Telethon-клиент для поиска папок и загрузки истории;
4. оркестратор отчётов;
5. Codex CLI client с двумя специализированными контрактами анализа;
6. атомарное минимальное состояние в JSON-файле;
7. внутрипроцессную блокировку от параллельных запусков.

PostgreSQL, Alembic, постоянный Telegram collector, очередь заданий и отдельный
worker из целевой runtime-архитектуры удаляются.

Постоянно активны только Telegram Bot API polling и планировщик. MTProto-загрузка
и Codex-анализ выполняют существенную работу лишь во время формирования
отчёта. Два вида анализа запускают отдельные изолированные вызовы Codex, но не
создают два постоянно работающих AI-процесса.

## 5. Поток формирования отчёта

Для ручного или планового запуска:

1. Проверить owner-only доступ для ручного запуска.
2. Попытаться занять общую блокировку анализа.
3. Если другая задача выполняется, сообщить её вид и время запуска без создания
   второй задачи.
4. Найти требуемую Telegram-папку.
5. Получить список допустимых источников и предупреждения по пропущенным
   источникам.
6. Зафиксировать единые границы 24-часового окна.
7. Загрузить подходящие сообщения из каждого источника.
8. Если данных нет, отправить понятное сообщение и не вызывать Codex.
9. Нормализовать и разбить вход на части в пределах установленного бюджета.
10. Последовательно проанализировать части через Codex.
11. При необходимости выполнить многоуровневое сведение результатов.
12. Провалидировать финальный структурированный результат.
13. Отформатировать и отправить отчёт частями с учётом лимитов Telegram.
14. Атомарно обновить состояние запуска и освободить блокировку.
15. Удалить временные файлы независимо от результата.

## 6. Контракт дайджеста

Дайджест по папке `Посты` содержит:

- период анализа, число источников и число обработанных публикаций;
- ключевые события за 24 часа;
- основные тезисы авторов;
- упомянутые бумаги, валюты, сырьё и макроэкономические темы;
- явно заявленные торговые идеи и ожидания;
- существенные противоречия между источниками;
- краткий итог и темы для дальнейшего наблюдения;
- ссылки на наиболее важные исходные публикации, когда они доступны.

Модель не должна придумывать события, позиции или ссылки, которых нет во
входных данных.

## 7. Контракт настроения рынка

Отчёт по папке `Чаты` содержит:

- индекс настроения от 1 до 10;
- словесную категорию;
- развёрнутое описание общего эмоционального фона;
- причины оптимизма;
- причины страха и сомнений;
- доминирующие темы и ожидания;
- разногласия между участниками;
- признаки перегрева или чрезмерного страха;
- краткий итог для наблюдения.

Интерпретация шкалы:

- 1–2 — паника и сильный страх;
- 3–4 — негатив;
- 5 — нейтральное настроение;
- 6–7 — умеренный оптимизм;
- 8–9 — сильная эйфория;
- 10 — предельная эйфория.

Оценка основывается только на содержании сообщений и характеризует настроение
участников чатов, а не объективное состояние рынка или движение цен. В отчёте
должно быть краткое обоснование выставленного индекса.

## 8. Статус и минимальное состояние

Кнопка `Статус` показывает:

- доступность бота, MTProto и Codex;
- наличие папок `Посты` и `Чаты`;
- количество допустимых источников в каждой папке;
- текущую задачу и время её начала;
- время, продолжительность и результат последних запусков;
- количество источников и сообщений в последних запусках;
- расписание 15:00 и 16:00 по Самаре;
- последнюю безопасную ошибку без секретов и содержимого сообщений.

Постоянный JSON-файл хранит только эти операционные метаданные. Обновление
выполняется через временный файл и атомарную замену. Сырые сообщения, ответы
Codex, токены, телефоны и данные авторизации в JSON не записываются.

## 9. Конкурентность и ошибки

Одновременно разрешена только одна тяжёлая задача анализа. Повторное нажатие
кнопки или совпавший плановый запуск не создаёт параллельный Codex-процесс.

Обработка ошибок:

- отсутствующая папка — явное сообщение с ожидаемым названием;
- пустая папка — отчёт не запускается;
- отсутствие сообщений за 24 часа — информационный ответ без вызова Codex;
- временная ошибка Telegram — ограниченные повторы с задержкой;
- FloodWait — ожидание только в установленном безопасном пределе, иначе
  контролируемая ошибка;
- ошибка части Codex или невалидный структурированный результат — весь отчёт
  считается неуспешным и частичный результат не публикуется;
- ошибка отправки Telegram — ограниченный повтор с сохранением безопасного
  статуса ошибки;
- остановка контейнера — корректная отмена задачи, закрытие клиентов и очистка
  временных файлов.

## 10. Хранение и безопасность

Остаются три постоянных Docker volume:

- MTProto session;
- Codex authentication;
- runtime state JSON.

Временные данные анализа размещаются в отдельном временном каталоге контейнера
и удаляются после завершения. Секреты не выводятся в логи. Контейнер не получает
доступ к `/root/bots` и не изменяет существующие сервисы сервера.

## 11. Переход с текущей версии

Переход выполняется без немедленного удаления данных:

1. Реализовать и проверить новый одноконтейнерный режим локально.
2. Сохранить существующие MTProto и Codex volumes.
3. Развернуть обновлённый образ на сервере.
4. Остановить старые `app`, `worker` и `postgres`.
5. Запустить новый `app` и проверить статус, папки, кнопки и расписание.
6. Выполнить по одному реальному ручному отчёту каждого типа.
7. Оставить старый PostgreSQL volume как резервную копию.
8. Удалять PostgreSQL volume только по отдельному подтверждению владельца после
   периода стабильной работы.

Команда `docker compose down -v` во время перехода запрещена, поскольку она
удалит также MTProto и Codex credentials.

## 12. Проверки

Автоматические тесты должны покрывать:

- поиск Telegram-папок и нормализацию имён;
- фильтрацию типов источников;
- точные границы 24-часового окна;
- исключение пустых и служебных сообщений;
- разбиение и многоуровневое сведение больших входов;
- структуру дайджеста;
- диапазон и обоснование индекса настроения;
- owner-only кнопки;
- ручные и плановые запуски через общий путь;
- запрет параллельных запусков;
- атомарное состояние и восстановление после повреждённого JSON;
- безопасные ошибки и отсутствие секретов в логах;
- разбиение длинного ответа на сообщения Telegram.

Проверка на сервере включает:

- валидную конфигурацию;
- сохранённые MTProto и Codex authentication;
- Codex preflight;
- обнаружение обеих папок и подсчёт источников;
- ручной дайджест;
- ручной отчёт настроения;
- кнопку статуса;
- отсутствие PostgreSQL и worker среди работающих контейнеров;
- отсутствие ошибок и циклов перезапуска в логах нового `app`.

## 13. Критерии готовности

Решение считается готовым, когда:

- один контейнер стабильно обслуживает кнопки и расписание;
- отчёты используют только источники из соответствующих Telegram-папок;
- оба отчёта анализируют ровно последние 24 часа;
- плановые отчёты приходят владельцу в 15:00 и 16:00 по Самаре;
- ручные кнопки формируют те же отчёты по актуальному окну;
- настроение содержит индекс 1–10 и развёрнутое объяснение;
- PostgreSQL и отдельный worker не работают;
- сырые сообщения не сохраняются постоянно;
- существующие боты в `/root/bots` продолжают работать.

## 14. Вне области задачи

- веб-интерфейс;
- несколько владельцев;
- публикация в отдельный Telegram-канал;
- долгосрочная история сообщений и отчётов;
- сравнение настроения с предыдущими днями;
- анализ изображений, видео и голосовых сообщений;
- горизонтальное масштабирование и распределённая очередь.
